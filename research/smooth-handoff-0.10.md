# 0.10.0 · 화면 인계와 끝점 해제

현재 후속 설치본은 **0.10.3-continuous-optics**입니다. 아래 0.10.0 결과만으로 중간 반전 문제를 해결했다고 판정하지 않습니다. 후속 자동 재현에서 남은 문제가 발견됐고, 이 문서 끝에 수정과 재검증을 기록했습니다.

2026-09-11. 0.9.3에서 사용자가 확인한 끊김, 중간 반전의 다른 비율 노출, 블러 급해제를 수정했습니다. 현재는 실기 검증 중이며 사용자 기준 충족을 확정하지 않았습니다.

## 수정

- `NativePanel.snapshot`: 들어올 패널에 표시하던 합성 결과를 원래 패널 크기의 HardwareBuffer에 GPU로 보관합니다. 다른 패널의 원본 이미지를 바로 맞춰 그리는 대신, 이 이미지를 유지하다 대상 크기의 새 화면으로 240ms 동안 인계합니다. 각 전환 세대가 바뀌면 이전 비동기 결과를 버립니다. 보관 이미지는 전환 종료 후 해제합니다.
- `AngleSmoother`: 자이로 목표값과 화면에 표시할 값을 분리했습니다. 방향이 바뀌어도 현재 표시 값에서 이어지며, 끝점에서도 즉시 0/180으로 점프하지 않습니다. 일반 이동의 시정수는 45ms, 끝점은 85ms입니다. 화면이 아직 준비되지 않았다면 끝점 보정을 인계 시작까지 미룹니다.
- `FoldService`: 센서·캡처·인계 콜백에서 즉시 중복 렌더링하던 요청을 Choreographer에 모읍니다. Vsync 전달이 없을 경우 24ms 대체 예약이 동작합니다. 캡처 완료 뒤 고정 33ms를 더 기다리던 동작도 제거했습니다. 정지 중 캡처 간격은 80ms입니다.
- 끝점 효과가 수렴하고 새 화면을 제출한 뒤 오버레이를 해제합니다. 기존 100ms 각도 보정과 160ms 투명도 해제를 별도로 실행하던 경로를 제거했습니다. 자이로 보정 파일이 없는 모드는 300ms 해제를 사용합니다.

두 패널 고정 매핑, 시스템 미러와 입력 전달, 공개 센서의 물리 전환 결정, 보안 콘텐츠 제외, 5분 자동 종료 및 독립 복구는 유지했습니다. 자이로는 광학 효과에만 영향을 주며 논리 화면 크기 전환을 결정하지 않습니다.

## 확인한 결과

- 빌드, Java 테스트 29개, Python 테스트 7개, Android lint 통과. 새로운 테스트는 끝점에서 한 프레임에 해제되지 않음, 현재 표시 값에서의 반전, 정지 목표값의 수렴을 확인합니다.
- 설치본 `0.10.0-smooth-handoff`, 코드 26.
- 실기 로그에서 GPU 화면 보관 16회가 24~62ms에 완료됐고 대상 프레임 준비는 292~406ms였습니다. 해당 로그의 Poldy/AndroidRuntime 오류는 없었습니다.
- 최초 정지 상태 자동 왕복의 끝점 보정은 준비 완료 후 약 0.5초에 걸쳐 수행됐고, 실제 앱 인계 시 표시 값은 약 179.5°/0.5°였습니다. 이 값은 시각 효과 입력이며 실제 힌지 각도 측정치가 아닙니다.
- 이후 녹화 중 실제 접힘과 중간 반전이 발생했습니다. 자동 왕복과 실제 동작을 완전히 분리한 비교 실험으로 보지 않습니다.
- 내부 녹화 420프레임, 외부 514프레임에 전체 검정 판정 표본은 없었습니다. 블러가 여러 프레임에 걸쳐 해제되는 표본도 확인했습니다. 물리 OLED 깜빡임, 체감 부드러움, 모든 앱의 중간 반전 회귀 해소는 사용자 관찰과 함께 판정해야 합니다.

근거: `measurements/native-v26-run/verification.json`, `logcat.txt`, `inner.mp4`, `outer.mp4`, 각 `*-frames/contact.jpg`. 진단 녹화는 축소본이며 실제 표시·GPU 보관은 내부 2448×1848, 외부 1248×1972입니다.

## 남은 제약

이 구현은 다른 앱의 내부·외부 두 레이아웃을 동시에 실행하지 않습니다. 전환 중 이전 화면을 잠시 보관하며, 새 화면의 크기와 두 프레임 확인만으로 임의 앱의 내부 배치 완료까지 보장할 수 없습니다. 비활성 패널은 현재 앱의 보호된 확산 미리보기를 표시합니다. 실제 힌지 각도 대신 주 자이로를 사용하므로 잡는 방법과 기기 전체 회전의 영향도 남습니다.

## 0.10.1/0.10.2 · GPU 부담 감소

선명한 화면·마스크·음영은 원본 해상도로 처리하고, 넓은 Gaussian 확산의 중간 버퍼만 가로·세로 절반으로 계산합니다. 내부의 미세한 내용 이동은 같은 역매핑을 64×40 격자로 근사하고, 움직이지 않는 면은 원본 이미지를 직접 그립니다. 외부의 이동은 기존 셰이더를 사용합니다. 효과의 경계·강도·기울기 입력은 연속값을 유지합니다.

별도 Android instrumentation이 생성한 GPU 이미지로 각도를 연속 변화시키며 원본/최적화 순서를 교대로 측정했습니다. 워밍업을 제외하고 방식·패널별 288회씩입니다.

| GPU 렌더링과 완료 대기 | 기존 중앙값 | 최적화 중앙값 | 기존 p95 | 최적화 p95 |
| --- | ---: | ---: | ---: | ---: |
| 외부 1248×1972 | 10.09ms | 7.64ms | 19.44ms | 10.43ms |
| 내부 2448×1848 | 35.68ms | 20.95ms | 47.06ms | 25.93ms |

이는 독립 GPU 렌더링 비교이며 실제 앱 전체 FPS 보장이 아닙니다. 생성 이미지 0/45/90/135/180°에서 완전히 선명한 끝점은 기존과 픽셀이 동일했습니다. 최적화된 내부의 정지 면 중앙도 각도 간 픽셀 차이가 없었습니다. 기존 셰이더의 같은 영역과는 일부 픽셀에서 최대 1/255 반올림 차이가 있습니다. 전체 이미지의 평균 RGB 차이는 표본별 0~0.82/255였고, 움직이는 영역은 격자 근사에 따른 차이가 남습니다.

근거: `measurements/renderer-v27-hardware/report.json`, `comparison.jpg`, `timing.json`. 도구: `app/src/androidTest/java/dev/poldy/lab/RendererBenchmark.java`, `tools/renderer_report.py`. 시험 도구는 생성한 픽셀만 사용하며 물리 화면을 캡처하거나 상태를 변경하지 않습니다. 단, 명시적으로 실행하는 instrumentation은 대상 앱 프로세스를 다시 시작하므로 애니메이션 서비스 중지 후 사용해야 합니다.

## 0.10.2 · 빠른 반전의 이미지 수명 수정

160ms에 반대로, 380ms에 원래 목표로 되돌리는 진단 동작을 추가했습니다. 실제 센서 동작에는 영향을 주지 않는 명시적 DIAGNOSE 옵션이며, 물리 접힘 신호가 들어오면 남은 진단 동작을 취소하고 정상 센서 동작을 따릅니다. 3초 뒤 시작 시 논리 화면으로 복귀합니다.

이 시험에서 0.10.1은 내부 패널에 좁은 앱 화면과 반쪽 화면이 잠깐 비쳤습니다. 초기에는 앱 배치 준비 조건을 의심했지만, 레이어 추적에서 Poldy 패널이 위에 유지되는 것을 확인했고 더 직접적인 원인을 찾았습니다. 이전 보관 이미지는 200ms 뒤 해제됐지만, 반전 후에도 다른 패널의 `bakedBefore`가 이를 참조하고 있었습니다. 그 상태에서 GPU 보관 이미지를 다시 만들면 투명한 이미지가 생겼습니다.

`FrameRetirement`는 최신 프레임·현재 전환·양쪽 패널의 참조를 모두 확인합니다. 어느 쪽에서도 사용하지 않고 유예 기간이 지난 뒤에만 해제합니다. `NativePanel`은 이미 해제된 보관 이미지를 투명 화면으로 처리하지 않고 오류로 감지합니다. 여러 반전 동안 이전 패널의 참조를 유지하는 경우와 마지막 사용 후 유예 기간을 포함한 네 가지 회귀 테스트를 추가했습니다. 빌드·Java 테스트 총 33개·lint가 통과했습니다.

같은 Poldy 화면의 자동 반전을 다시 녹화한 결과, 이전 0.10.1의 100ms 간격 표본 91개 중 4개에 보이던 예상 밖 검정 옆 여백/잘못된 배치가 0.10.2의 92개 표본에서는 나타나지 않았습니다. 가림 상태에서 새 배치로 이어지는 모습도 직접 비교했습니다. 이는 해당 자동 재현의 결과이며, 모든 앱과 실제 손동작의 문제가 해결됐다는 판정은 아닙니다.

추가로 최초 시스템 미러 버퍼가 아직 준비되지 않아 시작이 실패하는 사례를 재현했습니다. 시작 시의 `No logical buffer`에 한해 75ms 간격의 제한된 재확인을 적용했고, 실기에서 한 번 재확인한 뒤 정상 시작하는 것을 확인했습니다. 다른 캡처 오류나 기존 시작 제한 시간은 유지합니다.

근거: `measurements/native-v27-run/inner-frames/contact.jpg`, `measurements/native-v28-run/inner-frames/contact.jpg`, `reversal-comparison.json`, `verification.json`. 최신 APK: `artifacts/poldy-0.10.2-frame-ownership.apk`. 실제 다른 앱에서의 체감 결과는 사용자 확인을 기다립니다.


## 0.10.3 · 중간 정지 구간과 끝점 급가속 수정

사용자는 0.10.2에서 외부 왼쪽 블러 누락, 부족한 부드러움, 중간 구간에 정지해 있던 효과가 거의 완전히 펼치거나 접을 때 갑자기 움직이는 현상을 확인했습니다. 0.10.2를 사용자 기준 통과로 판정하지 않습니다.

코드에서 내부 효과의 강도가 0~94°에 고정되고 외부 효과는 88~180°에 고정되는 구간을 확인했습니다. 실제 연속 힌지 각도가 아닌 자이로 추정값에 이 곡선을 적용하면서, 큰 추정 오차가 끝점에 보정될 때 시각 변화가 집중될 수 있었습니다. 기존 외부 마스크는 최대 강도에서도 왼쪽 끝의 공간 가중치가 약 0.124에 불과했습니다.

- 양쪽 강도를 전체 0~180°의 연속 곡선으로 변경했습니다. 외부 확산 경계는 중간 진행에서 왼쪽 테두리 밖으로 이동하고, 이후에도 강도·반경·음영·내용 이동은 계속 변화합니다. 내부 정지 면의 선명함은 유지합니다.
- 표시 각도에 속도·가속도 제한을 적용했습니다. 끝점 보정의 목표 최대 속도는 140°/s, 가속도는 600°/s²입니다. 이동 중 속도가 더 컸다면 그 속도에서 감속하며, 단번에 0/180으로 변경하지 않습니다. 이 수치는 시각 효과 입력의 변화량이며 실제 힌지 속도가 아닙니다. 중간 정지는 목표값을 유지하며 시간만으로 접힘 진행도를 만들지 않습니다.
- 같은 중간 왕복에서 자이로 부호마다 서로 다른 보정 배율을 적용하던 계산을 수정했습니다. 한 물리 끝점에서 다음 끝점까지는 동일 배율을 사용해 동일한 앞뒤 회전에 인위적인 오차가 누적되지 않게 했습니다. 잡는 방식·기기 전체 회전으로 생기는 실제 추정 오차는 남습니다.
- 내부에서 확산 마스크가 0인 영역의 중간 GPU 합성을 생략합니다. 블러 경계에는 반경 3배의 원본 여유 영역을 남겨 잘림을 방지합니다. 선명한 이미지·정지 면의 원본 해상도는 유지합니다.

빌드·Java 테스트 38개·Python 테스트 7개·Android lint 통과. 새 회귀 검증은 양쪽 전체 구간의 반응, 외부 왼쪽 도달, 큰 끝점 보정의 양방향 속도, 늦은 렌더 프레임, 비대칭 보정 배율의 중간 왕복을 포함합니다.

새 효과 곡선으로 동일 GPU 생성 이미지를 각 방식·패널별 288회 비교했습니다. 전체 원본 효과와 최적화 효과의 내부 중앙값은 39.08→15.96ms, p95는 53.37→20.38ms였습니다. 외부 중앙값은 6.05→5.47ms, p95는 12.25→7.67ms였습니다. 이는 0.10.2와의 앱 FPS 비교가 아니라 새 효과에 대한 독립 GPU 처리·완료 대기 비교입니다. 0/45/90/135/180° 표본에서 완전히 선명한 끝점은 픽셀이 같고, 내부 정지 면 중앙은 각도가 달라도 픽셀이 같았습니다. 전체 평균 RGB 차이는 0~0.995/255입니다. 외부 90°의 왼쪽까지 확산된 모습도 이미지를 열어 확인했습니다.
