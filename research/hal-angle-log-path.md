# Samsung HAL 로그의 중간 접힘 각도 · 2026-09-11

## 새로 확인한 경로

일반 센서 등록 API가 거부되는 것과, 현재 펌웨어의 모든 출력 경로에서 각도 값을 얻지 못하는 것은 같은 결론이 아니다. `dumpsys sensorservice`에서는 전용 값이 가려져 있었지만, **현재 연결된 SM-F971N의 기존 `sensors-hal` logcat에는 중간 접힘 각도로 보이는 수치가 기록돼 있었다.** 로그 레벨 설정이나 보안 정책 변경 없이 ADB에서 읽었다.

예시:

```text
[0]folding_angle ts=1436653016881826 ns value [124/0] ...
[0]folding_angle ts=1436653936873910 ns value [113/0] ...
[0]folding_angle ts=1436655136872556 ns value [101/0] ...
[0]folding_angle ts=1436655296895420 ns value [ 89/0] ...
[0]folding_angle ts=1436655416865264 ns value [ 78/0] ...
[0]folding_angle ts=1436655536871149 ns value [ 62/0] ...
```

`folding_angle`의 첫 번째 필드와 `lid_angle_fusion`의 두 번째 필드가 거의 같은 시각에 비슷한 각도로 변한다. 이는 Poldy 자이로 추정값을 다시 읽은 결과가 아니라, 별도 Samsung 센서 HAL 프로세스의 기존 출력이다. 실제 물리 각도계와 비교한 절대 오차는 아직 측정하지 않았다.

## 확보한 기록

| 입력 | 이벤트 | 서로 다른 각도 수 | 값 범위 | 2초 미만 이벤트 간격의 중앙값 |
| --- | ---: | ---: | ---: | ---: |
| folding_angle | 83 | 68 | 1–180 | 약 200ms |
| lid_angle_fusion | 91 | 75 | 3–178 | 약 160ms |

위 숫자는 로그에 남은 과거 동작의 표본이다. 센서의 전체 갱신률이나 보장되는 최악 지연을 의미하지 않는다. 로그가 모든 센서 이벤트를 출력하는지 검증되지 않았으므로 이를 60Hz 센서로 표현하지 않는다. 빠른·느린 접힘, 정지, 반전, 손잡이 변경에서 추가 확인해야 한다.

## 실시간 검증 도구

[HalAngleProbe.java](../tools/HalAngleProbe.java)는 ADB shell에서만 실행되며, 기존 HAL 로그를 읽고 다음 값만 출력한다.

- 로그 종류와 중간 각도 값
- 센서 timestamp와 기기에서 읽은 timestamp
- 두 timestamp의 차이인 age_ms

2초보다 오래된 버퍼 기록, 미래 timestamp, 시간 역전, 0–180 범위 밖 수치는 버린다. 종료 시 로그 자식 프로세스를 정리한다. 센서 등록·화면 전환·권한·로그 설정을 변경하지 않는다. 물리 동작 시험에는 사용자의 손 조작이 필요하다.

첫 실시간 수집 구간에는 새 각도 이벤트가 없었다. 초기 Java 수집기는 타이머에서 blocking pipe를 닫는 종료 경로가 끝나지 않아 외부 timeout으로 종료됐고, 잔여 프로세스가 없음을 확인했다. 이를 별도 OS timeout으로 수정한 뒤 3초 정지 시험에서 started→finished, exit 0을 확인했다. 이 종료 검증은 실제 움직임에서의 값·지연 검증이 아니다. 후속 측정 결과는 아래에 기록했다.

## 90초 실시간 측정 완료

사용자가 완전 접힘·펼침·중간 정지·되접기를 수행한 두 번째 실시간 측정에서 **194개 표본, 115개 서로 다른 각도, 1–179°**를 수집했다. 센서 timestamp부터 같은 기기의 진단 프로세스 수신까지 중앙값 **1.461ms**, 95백분위 **4.791ms**, 최대 **56.507ms**였다. 각도가 달라진 표본 사이 간격의 중앙값은 **120.002ms**였다. 통신 지연과 표본 간격은 서로 다른 수치이며, 1.5ms가 애니메이션 전체 지연을 뜻하지 않는다.

중간 정지와 반전(예: 101→90→79→90→79)이 기록됐다. 90° 이후에도 101→113→125→137→147→159→169→179 등의 값이 나왔다. 이를 통해 이전 단일 자이로 추정처럼 90° 이후 각도 입력 자체가 끊기는 경로를 대체할 수 있음을 확인했다. 실제 물리 각도와의 절대 오차나 10° 미만 미세 움직임 추적은 아직 검증하지 않았다.

근거: [실시간 표본](../measurements/angle-alternative-paths/live-device-angles-2.jsonl), [통계](../measurements/angle-alternative-paths/live-summary-2.json).

## 0.12.0 앱 연결

Shizuku UID 2000 프로세스가 `main` 버퍼의 `sensors-hal` 태그만 읽는다. 두 검증된 기록 형식에서 각도·시각·출처를 파싱해 단방향 Binder 콜백으로 앱에 전달한다. 시작 전 기록, 500ms 초과 기록, 미래·역순 시각, 범위 밖 값은 버린다. 앱 수신 시에도 신선도를 다시 검사한다.

이전 `MotionAngleEstimator`는 애니메이션 실행 경로에서 제거했다. 자이로 X/Y/Z는 상대 기울기에 따른 평면 변형에만 사용한다. 수신된 HAL 각도를 `AngleSmoother`의 목표로 사용하며, 새 표본이 없으면 마지막 목표로 수렴해 정지한다. 다음 표본을 추측해 계속 진행하지 않는다. 완전 접힘·펼침에서는 공개 자세 신호로 0/180° 끝점만 보정한다. 패널 매핑과 논리 화면 전환은 기존 실제 자세 신호 경로를 유지한다.

읽기는 화면 공유 동의와 기존 4초 제어 임대 안에서만 시작하며, 정상 중지·임대 종료·Binder 클라이언트 종료에서 자식 logcat을 종료한다. 별도 OS timeout이 부모 강제 종료 때도 최대 300초로 읽기를 제한한다. 타 스레드의 blocking pipe close 대신 해당 자식 PID에 SIGTERM을 보내 읽기를 깨운다. 로그 설정·보안 정책·센서 등록 권한은 변경하지 않는다.

빌드, Java 테스트 49개, Android Lint(기존 경고, 오류 0개)를 통과했다. 실기에서 Shizuku 로그 읽기 시작을 확인했다. 정지 상태에서 시험 중지를 누른 뒤 reader_stopped와 native_stopped가 기록됐고, 자식 logcat·timeout·복구 감시 프로세스가 남지 않았으며 CLOSED·물리 크기 1248×1972로 복구됐다. 실제 움직임 중 앱 메인 스레드까지 265개 표본·135개 각도를 받았다. 센서 기록→앱 수신 지연 중앙값 1.020ms, 95백분위 5.072ms, 최대 23.935ms였다. 렌더링/보간 지연은 별도다. 끝점 신호 때 표시 각도의 잔여 거리 중앙값은 17.54°, 최대 28.08°였다. 이전 0.11.2의 100° 이상 오차는 이 측정에서는 나오지 않았지만, 조기 종료와 늦은 시작이 남는 원인을 추가로 확인했다. [실기 로그](../measurements/native-v33-run/live-logcat.txt), [통계](../measurements/native-v33-run/summary.json).

## 0.12.1 시작·종료 판단 보완

실기 로그에서 공개 자세가 HAL 157° 부근에서 이미 OPENED로 바뀌었고, 닫는 방향으로 HAL 169→167→154→141→128°가 도착하는 동안에는 기존 moving 플래그가 false였다. 단지 각도 목표만 HAL로 교체하면 첫 부분을 건너뛰는 문제가 남는다.

`HingeProgress`를 추가했다. 이전 끝점에서 멀어지는 HAL 각도로 새 동작을 시작하며, 뒤늦은 공개 자세 OPEN/CLOSE는 같은 전환을 재시작하지 않는다. 중간 반전은 표시 각도만 역방향으로 움직이고 화면 비율을 매번 바꾸지 않는다. 실제 자세의 끝점 신호는 필요한 논리 화면 복구에 계속 사용하되, 시각 효과에는 종료 후보만 제시한다. HAL 값이 끝점 3° 이내에 오면 0/180°로 부드럽게 마무리한다.

HAL 로그가 약 10–12° 변화마다 기록되어 최종 작은 변화가 생략될 수 있다. 따라서 끝점 자세가 있고 마지막 값도 끝점 12° 이내인 경우에만, 새 값과 자세가 350ms 조용히 유지되면 잔여 부분을 보정한다. 20° 이상 남은 값을 시간만으로 끝까지 밀어 버리지 않는다. 이는 마지막 수 도의 측정 누락을 다루는 제한된 보정이지 정밀 각도계 검증을 대신하지 않는다. 완료 뒤 도착한 같은 방향의 최종 로그가 새 동작을 다시 시작하지 않도록 했다.

0.12.1 빌드·Java 테스트 55개·Lint 통과(기존 경고, 오류 0개). 실기에서 46개 표본을 확인했고 5°에서 펼침, 163°에서 접힘을 시작했다. 양 끝점의 잔여 보정은 이 시험에서 7°/8°였고 오류 로그는 없었다. 사용자는 “예전이랑 다르게 잘 따라오는데 … 중간 중간에 끊겨서” 보인다고 확인했다. [실기 기록](../measurements/native-v34-run/snapshot-logcat.txt), [분석](../measurements/native-v34-run/summary.json).

## 0.12.2 표본 사이 정지 완화

같은 시험에서 각도는 161→149→137→125°처럼 약 12° 간격으로 기록됐다. 이 구간의 갱신 간격은 200–440ms였다. 이전 50ms 시간 상수의 보간은 다음 기록 전에 목표에 도착해 멈추는 구간을 만들었다. 렌더 제출의 CPU 평균은 대체로 수 ms였지만 이는 GPU 합성 완료 시간이나 실제 표시 프레임 측정을 대신하지 않는다.

`AngleSmoother`의 이동 시간 상수를 표본 간격에 따라 85–180ms 범위에서 조절하도록 수정했다(초기 120ms). 거의 동시에 들어오는 두 HAL 형식의 중복 기록이 시간 상수를 줄이지 않도록 약 8° 이상 움직인 표본으로 간격을 계산한다. 긴 정지는 시간 상수 확대에 포함하지 않는다. 새 표본이 없으면 마지막 각도로 수렴하고, 속도로 미래 각도를 외삽하지 않는다. 0/180° 종료 보정의 속도 제한과 기존 화면 전환 보호는 유지한다.

0.12.1의 동일 표본을 8ms 간격으로 두 구현에 재생했다. 다음 표본까지 500ms 이하이고 각도 변화가 3° 이상인 구간의 765프레임 중, 프레임당 변화 0.01° 미만인 구간은 이전 74프레임에서 수정 후 1프레임으로 감소했다. 이는 입력 재생 계산 결과로, 실제 폰의 프레임 누락률이나 사용자 체감 검증 결과는 아니다. 부드러움의 대가로 움직임을 조금 더 늦게 따라오는 보간 지연이 생긴다. [재생 결과](../measurements/native-v35-smoothing/replay-summary.json), [시계열](../measurements/native-v35-smoothing/replay.csv), [재생 소스](../measurements/native-v35-smoothing/replay-source/Replay.java).

빌드·Java 테스트 57개·Lint 통과(기존 경고, 오류 0개). 0.12.2 설치(versionCode 35)와 실행을 확인했다. 첫 전환에서 158개 HAL 표본을 앱으로 받았고 앱 수신 지연 중앙값은 1.165ms였다. 필터링한 시험 로그의 오류는 0개다. [실기 기록](../measurements/native-v35-smoothing/live-logcat.txt), [통계](../measurements/native-v35-smoothing/summary.json). 사용자에게 끊김 감소와 추종 지연 체감을 확인 중이다.

## 경로의 한계

이 경로는 비공식 로그 형식에 의존하므로 펌웨어 변경이나 출력 중단 시 깨질 수 있다. 현재 측정된 갱신 간격에 맞춰 앱에서 표본 사이 보간을 적용했다. Android 일반 앱의 로그 접근 권한과 ADB shell의 로그 접근 권한을 혼동하면 안 된다.

애니메이션은 이런 실제 센서 기반 표본을 기준으로 삼고 표본 사이만 부드럽게 연결해야 한다. 한쪽 자이로를 큰 계수로 확대하여 끝까지 추정하는 기존 방식과 다르다. 그래도 로그 표본이 드문 구간의 움직임을 정확히 알 수 있는 것은 아니므로, 멈춤·반전·보간 지연을 별도로 검증해야 한다. 0.12.0에서 애니메이션에 연결했으며, 실제 시각 품질과 앱 전달 지연은 별도 검증한다.

## 이전 진단에서 그대로 유효한 사실

`SensorAccessProbe.java`에서 공개 힌지 등록은 성공했고, 전용 각도·보조 가속도계·보조 자이로는 실제 SSENSOR 권한 부족으로 거부됐다. 공개 힌지의 메타데이터 해상도는 90이다. 부트로더는 잠겨 있으며 현재 shell은 UID 2000이다. 이들은 새 로그 접근 경로를 부정하는 증거가 아니다.

Samsung 문의는 사용자 요청에 따라 진행하지 않는다. 문의 내용이나 로그를 외부로 전송하지 않았다.
