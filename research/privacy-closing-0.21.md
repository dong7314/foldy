# Foldy 0.21.2: 보호 화면과 접힘 전환

2026-09-14, Samsung SM-F971N / Android 17. 사용자는 배포·push를 나중에 직접 요청하기로 했고, 회전 정책 변경은 원하지 않았다. 이번 변경은 보안 감사의 실행 중 보호와 접을 때의 정지 구간에 집중한다. 기존 미커밋 작업을 보존했으며 commit, push, 배포는 하지 않았다.

## 설치본

- 버전: 0.21.2, versionCode 79, Shizuku UserService version 79.
- APK: `artifacts/foldy-0.21.2-privacy-motion.apk`.
- SHA-256: `a5ba91d12a4305c40590290e2ec698fc38ca12b82028186f6e2e677b17628b48`.
- 휴대전화에서 설치 APK를 다시 가져와 로컬 빌드와 해시 일치를 확인했다.
- 배포용 서명과 `debuggable` 변경은 이번 범위에서 제외했다. 현재 APK는 개발 시험판이다.

## 실행 중 보호

`WindowInfosListener`의 창 메타데이터 알림으로 FLAG_SECURE와 `SENSITIVE_FOR_PRIVACY`를 확인한다. 이 기기에서는 FLAG_SECURE를 켰을 때 동일 Activity의 inputConfig가 `0`에서 `0x40000`으로 변했다. 화면 내용이나 창 제목을 분류·저장하지 않으며, 무거운 `dumpsys window`를 반복 실행하지 않는다.

`setHideOverlayWindows(true)`의 실제 상태는 이 알림에 포함되지 않았다. 따라서 **HIDE_OVERLAY_WINDOWS 권한을 가진 앱이 보이면 해당 앱 전체에서 효과를 일시 정지**하는 보수적인 정책을 쓴다. 사용 중인 화면이 안전하더라도 이 권한을 선언한 앱에서는 효과가 쉬어갈 수 있다. Android의 [민감한 창 보호 설명](https://developer.android.com/security/fraud-prevention/activities)과 같이 보안 캡처 차단과 오버레이 차단은 별개의 정책이다.

보호 신호가 들어오면 shell이 소유한 상위 SurfaceControl을 먼저 숨긴다. 앱에 전달하는 것은 하위 버퍼 핸들뿐이므로, 이전 프레임의 지연된 alpha 변경이 상위 숨김을 해제할 수 없다. 보호 중에는 새 장면 생성과 캡처도 차단한다. 캡처 전후 보호 epoch가 달라졌으면 결과 버퍼를 버린다. 합성 레이어 자체도 secure surface로 만들었다.

앱은 원격 화면 복구를 기다리기 전에 양쪽 효과 레이어와 프레임 캐시를 해제한다. 진행 중인 GPU 작업이 참조하는 원본만 작업 완료까지 보유한 뒤 폐기하고, 이전 세대의 콜백은 새 장면에 적용하지 않는다. 일반 화면으로 돌아오면 새 원본 프레임을 준비해서 재개한다. 펼친 상태에서 재개할 때 각도 보간기가 0°부터 잘못 움직이지 않도록 초기 각도를 맞춘다. 중간 자세에서는 정상 끝점까지 재개를 기다린다.

기존 Shizuku provider와 비공개 서비스 경계에 더해, `DisplayControl.onTransact()`에서 AIDL 인자나 SurfaceControl 핸들을 읽기 전에 호출 UID를 검사한다. Foldy 소유 UID만 제어 연산을 호출할 수 있고, shell 자신에게는 Shizuku의 destroy 호출만 허용한다.

움직이지 않을 때 캡처 목표 간격을 80ms에서 240ms로 늘렸다. 접힘 동작 중에는 기존 16ms 목표를 유지한다. **일반 화면의 캡처가 완전히 없어졌다는 뜻은 아니다.** 시작 장면을 준비하기 위한 GPU 버퍼는 계속 필요하다. 화면을 파일로 저장하거나 네트워크로 전송하는 기능은 추가하지 않았다.

설정 화면에는 일시 정지를 구분해 표시하고, 준비 중·일시 정지 중에도 끄기 버튼을 제공한다.

## 접을 때 멈춰 보이던 구간

기존 실제 접힘 기록에서는 보관 이미지 준비가 29~42ms에 끝났지만 대상 앱의 프로필은 약 0.7~1.0초 뒤에 준비됐다. 기존 `NativePanel.hold()`는 블러·명암·기울기까지 이미 구워진 이미지를 그동안 그대로 표시했다. 각도 보간기가 움직여도 해당 이미지의 효과는 고정되어 있었다.

이제 `snapshotRaw()`는 대상 패널 크기의 **효과 없는 원본 이미지**를 화면 밖에서 만든다. 준비 중에도 `frame()`, 새 앱 화면과 섞는 동안에도 `blend()`로 동일한 FoldOptics를 적용한다. 원본에는 블러나 기울기 변형을 중복 적용하지 않는다. 원래의 화면 비율 검사, 전환 세대 검사, 양쪽 프레임 표시 완료 후 프로필 변경, 밝기 복구 정책은 유지했다.

## 검증

0.21.0의 첫 실제 펼침에서는 종료 직후 시스템 `ColorFade BLAST_d1` 레이어가 보호 창으로 오인돼 효과가 일시 정지했다. 사용자가 “실행했는데도 애니메이션이 안 보인다”고 확인했다. 0.21.1은 **시스템 UID 1000, type 0, flags 0, 입력 채널 없음, 확인된 ColorFade 레이어 이름**이 모두 일치하는 전원 전환 스냅샷만 제외한다. 일반 앱의 보안 창과 이름을 흉내 낸 다른 UID에는 이 예외를 적용하지 않는다. 이 조건을 추가한 뒤 같은 보안 Activity 전환 시험을 다시 통과했다. 0.21.0을 정상 실사용 검증 완료로 해석하면 안 된다.

- 단위 테스트 112개 통과. UID 경계, 보안 플래그 변화, 숨겨진 창·미러 제외, Foldy 자체 type-0 버퍼 제외, 펼침 재개 초기 각도, 일시 정지 UI 상태를 포함한다.
- lint 오류 0, 경고 42. debug APK와 instrumentation APK 빌드 통과.
- APK DEX의 정의 목록을 읽어 compileOnly 프레임워크 스텁이 패키징되지 않은 것을 확인했다.
- 실제 GPU에서 원본 준비의 해상도·색상 보존 및 같은 준비 이미지의 각도별 출력 변화를 확인했다. 이미지 파일 대신 합성 픽셀 표본만 검사했다.
- 합성 GPU 닫힘 루프: 외부 p50 4.77ms / p95 6.68ms, 내부 p50 8.59ms / p95 13.80ms. 이는 개별 패널의 합성·펜스 완료 시간이며 전체 제품 FPS나 전환 지연으로 해석하지 않는다. 내부 화면의 고주사율 프레임 부하에는 여지가 남아 있다.
- 실기에서 일반 테스트 Activity → 같은 Activity에 FLAG_SECURE → 해제 순서로 효과 중단·캐시 해제 경로·자동 재개 로그를 확인했다. 요청 후 보호 메타데이터 감지까지 해당 시험에서 44ms가 걸렸다. 모든 상황의 지연 상한이나 0프레임 노출 보장은 아니다.
- 0.21.1 재시험에서는 동일 보안 플래그 요청 후 19ms에 감지했고, 해제 후 새 패널을 만들어 재개했다. 보안 플래그와 HIDE_OVERLAY_WINDOWS 차단, 별도 앱 UID의 component 접근 거부를 모두 재확인했다.
- HIDE_OVERLAY_WINDOWS를 선언한 별도 테스트 앱에서도 중단하고, 일반 테스트 앱으로 복귀했을 때 재개했다. 이 앱의 hide 플래그가 false인 경우에도 중단하는 정책을 확인했다.
- 두 별도 테스트 앱 UID에서 provider 호출과 FoldService 바인딩은 모두 거부됐다. 직접 privileged Binder 핸들을 외부 앱에 전달하는 공격 시험은 하지 않았으며, 추가 onTransact 정책은 단위 테스트와 정상 실기 제어로 검증했다.
- 두 진단 APK는 시험 후 제거하고 Foldy로 돌아왔다. 실제 개인정보 화면은 보안 시험에 사용하지 않았다.
- 검은 깜빡임과 체감 끊김이 완전히 없어졌다고 판단하지 않는다. 아래 사용자 피드백은 0.21.1에 대한 것이며, 0.21.2의 첫 프레임 경합을 강제로 재현하는 실기 시험은 별도로 남아 있다.
- 0.21.1 실제 펼침·접힘에서 사용자는 “엄청 한꺼번에 움직이는 현상은 많이 줄었어”라고 확인했다. 로그에서도 내부·외부 프로필 준비와 각 끝점까지의 reveal 완료가 확인됐다. 이 피드백은 끊김이 완전히 사라졌다는 의미가 아니다.

0.21.1 시험 중 잠금과 빠른 전환이 겹친 구간에는 회전 복구 확인 불일치가 한 번 기록됐고, 이후 잠금 해제 직후 첫 프레임 전에 접힘 요청이 들어와 서비스가 중지됐다. 0.21.2는 후자의 요청을 첫 정상 프레임까지 보류하고 가장 최근 대상 패널로 이어간다. 사용자가 확인한 렌더러와 보안 창 판정은 0.21.1과 같다. 회전 선호를 덮어쓰거나 확인 실패를 무시하도록 바꾸지 않았다. 해당 복합 상황의 장시간 회귀는 남아 있다.

보호 신호를 제공하지 않는 앱의 민감한 내용을 자동으로 알아내는 기능은 없다. 숨겨진 API와 이 펌웨어에 의존하므로 다른 펌웨어로의 보안·동작 보증도 하지 않는다. 미지원 API에서는 보호 확인에 실패한 상태로 효과를 시작하지 않는다. 사용자 지정 제외 목록, 실제 인증·DRM·잠금과 접힘이 동시에 발생하는 장시간 시험, 배포용 서명·비디버그 검증은 후속 항목이다.

측정 파일은 Git 제외 경로 `measurements/privacy-closing-0.21/`에 있다: `baseline-folds.log`, `window-api.txt`, `privacy-events.txt`, `runtime-privacy.log`, `gpu-transfer.txt`, `after-folds.log`, `build.log`, `installed.apk`.
