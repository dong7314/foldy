# 0.19: 연속 수집, 기울기 효과와 밝기 충돌 수정

2026-09-14, macOS / SM-F971N / Android 17. 사용자가 요청한 순서대로 수집 수명,
기울기 효과, 영상에 따른 블러·경계 조정, 실사용 검증을 진행했다.
0.19.1에서 사용자는 애니메이션과 잠금 뒤 재개가 정상이라고 확인했지만 밝기가
들쑥날쑥하는 증상을 보고했다. 이에 따른 후속 수정본이 **0.19.2 (72)**다.

## 1. 5분 뒤 수집이 끊기는 문제

`HalAngleReader`와 `PanelLuminanceReader`가 각각 한 번만 시작하던 300초 logcat을
`RenewingLogcat`으로 교체했다. 자식 프로세스의 제한은 300초로 유지하면서 정상
만료 때 다음 자식을 시작한다. HAL의 최근 버퍼와 마지막 센서 시각은 이어받으며,
500ms보다 오래된 값·중복·역순 값은 기존 파서가 버린다. 재시작 실패는 세 번까지만
재시도하고, 앱 Binder 종료·잠금·명시적 중지는 재시작하지 않는다.

밝기 기록은 움직이지 않는 화면에서 5분 이상 새로 나오지 않을 수 있다. 현재
물리 패널과 nits를 다시 확인해 사용하며, HDR 이후 옛 SDR 기록을 재사용하지
않는다. DPC의 순간 OFF는 복구 대상이므로 직전 정상 SDR 기록을 유지한다.
새 자식이 재생한 과거 로그로 최신 상태를 되돌리지 않는다.

검증:

- `LogcatLifecycleProbe`: 실제 기기의 2초 임대에서 두 수집기가 각각 네 번
  시작되고, close 뒤 2.5초 동안 다시 시작하지 않았다. 잔여 자식 없음.
- 0.19.0을 6분 30초 기록했다. 300초 만료 뒤 밝기는 약 19ms, 각도는 약 10ms에
  새 자식이 시작됐다. 이후에도 서비스·원본 캡처가 이어졌다. 이 구간은 정지 화면
  시험으로, 갱신 순간에 움직인 각도의 손실률을 측정한 것은 아니다.
- 자료: `measurements/continuity-20260914-v70/`.

## 2. 실제 IMU 입력을 쓰는 효과

이전 `FoldRenderer.attitude/orientation`은 빈 메서드였다. `FoldViewMotion`이
상대 자이로 자세와 중력 방향을 받아 얕은 내용 이동, 확산 방향, 음영을 바꾼다.
힌지는 기존 HAL의 절대각을 쓰며 자이로를 힌지 각도로 재해석하지 않는다.

- 이동 상한은 화면 폭 0.4%, 높이 0.5%다. 작은 확대가 이동으로 생기는 빈틈을
  덮는다. 원근·사다리꼴·화면 종횡비 변형은 추가하지 않았다.
- 양 끝에서는 이동·확대·자세 음영이 정확히 0이다. 기울어진 채 끝나도 잔상이
  남지 않으며, 같은 입력으로 돌아오면 같은 픽셀을 만든다.
- 센서 값에는 기존 자세 보간을 적용하며 별도의 자동 진행 타이머는 없다.

## 3. 세 영상과 비교한 조정

세 원본의 추출 프레임을 다시 확인했다: 첫 영상 전체 펼침, 두 번째 영상의
시작·완료 세부 구간, 세 번째 영상의 닫기·느린 펼침, 네 가지 움직이는 면의
확대 자료. 파일은 `research/reference-frames/`와 `research/plane-study/`에 있다.
이는 영상의 시각적 관찰이며 기기 센서나 원 제작자의 코드를 추출한 결과는 아니다.

외부 오른쪽·내부 왼쪽으로 확산하는 방향은 유지했다. 블러 공간 입력을 약 10%
늘리고 약한 첫 층의 시작을 앞당겼다. 외부 왼쪽에는 매우 얕은 확산을 더해 효과가
전혀 없는 직선 띠를 줄였다. 상하 음영은 좁은 검정 띠 대신 넓게 퍼지며 기울기에
따라 조금 움직인다. 블러는 세 GPU 축소 버퍼를 연속 알파로 합성한다.

0.19.1의 실제 GPU 검증 (`measurements/renderer-v71/`):

- 44개 원본 해상도 생성 이미지. 실제 앱 화면을 저장하지 않았다.
- 자이로·중력 입력을 각각 바꾸면 다른 픽셀이 나오며, 반전 후 같은 각도·자세의
  출력은 동일했다. 기울어진 상태의 보이는 끝점도 원본과 동일했다.
- 1~2° 이탈부터 흐림이 관측됐다. 마지막 1°의 평균 RGB 차이는 내부 약 0.47,
  외부 약 0.71/255로 한 번에 사라지는 큰 픽셀 변화가 없었다.
- 검사한 밝은 상하 경계는 38~43단계, 한 픽셀의 최대 밝기 차이는 1/255였다.
  alpha는 모두 255였다. 가장 어두운 내부 끝은 4~10/255라 그 지점에 20단계
  이상의 명암을 요구한 초기 검사 위치를 실제 밝은 feather 위치로 교정했다.
- 최적화 렌더러 각 패널 288프레임: 외부 p95 7.37ms, 내부 p95 9.11ms.
  GPU 제출·fence까지의 단독 측정이며 앱 전체 FPS·물리 패널 무깜빡임을 뜻하지 않는다.

## 4. 실사용과 복구 검증

- 0.19.1 정지 상태에서 앱 강제 종료 후 약 0.82초 이내에 임시 레이어·수집 자식·
  장치 상태 override가 없어졌다. 전환 진행 중 강제 종료를 측정한 것은 아니다.
  `measurements/lifecycle-20260914-v71/crash-check.json`.
- 사용자가 실제 여러 번 접고 펼치고 잠금·해제를 수행했다. `native_paused`와
  `resumed=true`, 재개 이후 실제 연속 각도·전환을 확인했다.
- 사용자 피드백: 애니메이션과 재개는 정상, 밝기 출렁임은 남음.
- USB 연결 상태 약 7분 관찰에서 배터리 온도는 약 29.0~29.9°C, thermal status 0.
  메모리는 접힘 시험 중 약 545MiB까지 올라갔다가 정지 상태 약 201MiB로 내려왔다.
  충전 중인 짧은 시험이므로 방전률·하루 발열·메모리 누수 부재를 입증하지 않는다.
- 가로 영상·멀티 윈도우와 장시간 방전 시험은 아직 완료하지 않았다.

## 0.19.2: 자동 밝기와 충돌하던 고정 반복 제거

실기 자동 밝기 모드는 1이었다. 첫 전환에서 출력이 81.23→278.15→81.23nit로,
이후에도 278~290nit대와 81.23nit 사이를 빠르게 왕복했다. 0.18.6부터의 고정
밝기 반복이 정상 자동 밝기 변화까지 덮어쓰는 문제가 확인됐다.
`measurements/daily-20260914-v71/brightness-oscillation.json`에 구간별 기록이 있다.
같은 구간의 10회 전환에는 큰 양수 밝기가 20ms 이내에 원래 값으로 되돌아오는
A→B→A 명령이 63회 있었다. 이는 출력 명령 지표이며 눈에 보인 깜빡임 횟수가 아니다.

`LuminanceGuard`는 양수의 정상 출력에는 쓰지 않는다. OFF/-1/0 기록을 관측하면
최근 정상 SDR 값을 최대 한 번 복구하고, 새 정상 밝기는 그 값으로 이어받는다.
다른 패널·오래된 OFF·HDR·종료된 guard는 복구하지 않는다. 전환 직전 패널만,
private shield 동안 최대 1.5초라는 범위와 패널 전원 유지는 유지했다.
일반 밝기나 자동 밝기 설정은 변경하지 않았다.

95개 Java 테스트, Lint 오류 0/경고 35개, APK 빌드 통과. 0.19.2의 렌더러는
0.19.1과 동일하므로 위 GPU 검증을 그대로 적용한다. 수정본을 설치·실행했다. 첫 4분 수집에는 실제 접힘 전환이 없어 밝기 충돌 감소나
검은 깜빡임 회귀 여부를 판정하지 않았다. 사용자의 재시험 결과를 기다린다.
측정 폴더는 `measurements/brightness-guard-20260914-v72/`다.

## 후속 확인

- 0.19.2 밝기·검은 깜빡임에 대한 사용자 확인과 실기 출력 기록 비교.
- 자동 밝기가 패널을 바꾸며 정상적으로 크게 달라지는 상황과 앱의 충돌을 구분.
- 가로 영상, 멀티 윈도우, 빠른 반전 중 프로필·입력, 전환 중 앱 강제 종료.
- USB 충전과 분리한 장시간 배터리·발열·메모리 관찰.

이 문서는 구현·GPU 검사·실제 패널 출력 명령·사용자의 육안 확인을 구분한다.
원본 영상과 모든 앱에서 완전히 동일해졌다고 주장하지 않는다.
