## 추가 영상과 0.9.1

추가 영상 `1a08a212d3350598a.mp4`는 26.8667초, 720×720, 30 fps입니다. 0.25초 간격 108개를 추출해 기존 141개와 함께 총 249개 표본을 확인했습니다. `reference-frames/new-clip/frames.json`에 실제 디코딩 시각을 보관합니다.

- 약 2.23~2.73초, 9.50~10.00초: 외부 오른쪽의 흐림 범위와 어두워짐이 함께 커집니다.
- 약 10.50~11.00초: 내부 왼쪽의 어두운 영역이 드러난 뒤 걷히고, 오른쪽 내용은 상대적으로 선명합니다.
- 약 16.50~19.73초: 천천히 여는 동안 흐림 경계·강도·음영이 단계적으로 달라집니다.
- 약 21.73~22.73초, 24.25~25.23초: 빠른 접기·펴기에서도 물리 움직임에 맞춰 효과가 달라집니다.

힌지 데이터가 없는 촬영 영상이므로 정확한 각도별 수치를 역산했다고 주장하지 않습니다. 물리 패널의 원근을 화면 안에 다시 그리는 변형도 추가하지 않습니다. 구현한 광학 곡선은 시각적 관찰을 바탕으로 조정한 시작점입니다.

`FoldOptics`는 하나의 각도로 영역의 경계, 경계 폭, 확산 반경, 음영을 결정합니다. `FoldRenderer`는 선명한 원본에 약한 확산·강한 확산 두 층과 음영을 공간적으로 합성합니다. 내부 오른쪽은 효과 밖에 둡니다. 고정 시간으로 각도 진행을 만들어 내지 않습니다. 앱 크기 변경을 가리는 기존 프레임 인계와 끝점의 짧은 정리는 별도입니다.

`MotionAngleEstimator`는 일반 자이로 Y축 회전을 적분한 **추정** 입력입니다. 사용자의 3회 왕복 기록에서 펼침은 +6.5/+35.1/+33.3°, 접힘은 −22.5/−54.5/−64.6°의 센서 회전으로 관측됐습니다. 이는 힌지의 180° 이동과 다르며 잡는 방법에 따른 오차가 큽니다. 20° 미만 표본을 보정에서 제외하고 중앙값으로 펼침 5.2694배, 접힘 3.3043배를 적용했습니다. 전역 Y축 회전과 힌지 동작을 구분할 수 없고, 센서가 있는 쪽이 거의 움직이지 않으면 반응이 약할 수 있습니다. 공개 끝점 신호로 누적 오차를 초기화합니다.

미리보기의 0/45/90/135/180°는 수동 입력입니다. 135° 유지 및 180→135° 복귀에서 효과 영역의 픽셀 차이 0, 내부 오른쪽은 0→180° 사이에도 차이 0을 확인했습니다(`measurements/motion-calibration/renderer-check.json`). 이는 렌더러의 결정성과 선명 영역 보존 검증이며, 실제 각도 추정 정확도의 검증은 아닙니다.

## 두 번째 영상: 영역별로 일어나는 변화

### 1. 닫힌 상태: 약 0~2.0초

외부 화면의 위젯, 아이콘, 글자가 선명합니다. 완전히 펼친 뒤에도 같은 선명도 상태로 끝납니다. 끝점에 잔여 블러를 남기는 연출이 아닙니다.

### 2. 열기 시작: 약 2.0~2.5초

추가한 세부 표본에서 실제 2.073초는 대체로 선명하고, 2.140초에는 오른쪽 아이콘의 흐림이 확인됩니다. 따라서 눈에 띄는 시작을 약 2.07~2.14초 사이로 좁힐 수 있지만, 정확한 첫 효과 프레임이나 센서 기준 시점은 확정하지 않습니다. 2.207~2.473초에는 오른쪽 위젯과 아이콘의 흐림이 점차 넓고 강해집니다. 처음부터 화면 전체를 균일하게 강하게 흐리는 방식과는 다릅니다.

![시작 구간 세부 프레임: 라벨은 실제 디코딩 시각](/Users/ldong-yeop/Desktop/private/poldy/research/reference-frames/start-detail/contact.jpg)

흐림의 강도는 외부 화면 전체에서 같지 않습니다. 앞면의 오른쪽 위젯과 아이콘부터 넓게 흐려지고, 왼쪽 열 일부는 상대적으로 읽을 수 있습니다. 기기 테두리와 손은 또렷한데 화면 내용에 선택적으로 흐림이 나타납니다. 전체 촬영 영상의 초점 이동만으로 설명되는 현상은 아닙니다.

### 3. 앞면이 기울어진 상태: 약 2.5~3.75초

움직이는 앞면에 내용과 색이 계속 남습니다. 뒤에 드러나는 화면의 오른쪽 아이콘도 보입니다. 앞면의 흐림, 가장자리 어두워짐, 물리적인 가림이 함께 보입니다. 화면을 검은색으로 껐다가 다시 그리는 장면과는 차이가 있습니다.

이때 내용이 유리 너머로 보이는 듯한 인상이 있지만, 실제 투명 패널인지, 합성인지, 화면에 별도로 그린 효과인지는 확인할 수 없습니다. 이 인상을 재현하는 것과 해당 하드웨어가 실제로 투명하다는 주장은 구분해야 합니다.

### 4. 내부 화면이 드러나는 상태: 약 3.75~5.0초

흐림의 주된 위치가 내부 화면 왼쪽으로 바뀝니다. 오른쪽 아이콘·위젯은 비교적 선명하고 같은 묶음으로 유지됩니다. 왼쪽의 추가 위젯과 배경이 흐린 상태로 드러납니다.

따라서 화면 하나에 고정된 왼쪽 마스크만 쓰거나, 작은 화면 전체를 큰 화면 전체에 확대하는 방식은 맞지 않습니다. 외부 앞면과 내부 펼침 영역의 좌표계를 따로 다뤄야 합니다. 영상의 홈 화면은 확장 영역에 무엇을 그릴지 알고 있습니다. 일반적인 다른 앱은 넓은 화면에서 자체 규칙으로 레이아웃을 다시 계산하므로, 동일한 아이콘 위치 유지가 자동으로 성립하지 않습니다.

### 5. 펼침 끝의 선명도 회복: 실제 약 5.007~5.140초

실제 4.973초에는 왼쪽 위젯이 강하게 흐립니다. 5.007초에 흐림이 줄어들기 시작한 것으로 보이고, 5.040~5.073초에 글자와 위젯 형태가 더 읽히며, 5.140초에는 대부분 선명해집니다. 이 구간에서의 최종 해제는 대략 0.13~0.20초 규모입니다. 측정은 시각적 판독이며 정확한 셰이더 커브를 역산한 값은 아닙니다.

핵심은 강한 흐림을 이동 중에 유지하다가 끝에서 해제한다는 점입니다. 펼치기 시작하자마자 일정 시간 동안 흐림을 계속 줄이는 방식은 이 장면과 맞지 않습니다. 겉보기에는 거의 평평한 상태에서도 흐림이 잠시 남기 때문에, 단순히 물리 각도에만 비례한다고 확정해서도 안 됩니다. 끝점 판정 뒤 짧은 마무리 보간이 있을 가능성이 있습니다.

### 6. 닫기와 빠른 반복: 약 6.75~19.875초

느린 닫기 구간 약 6.75~8.75초에서는 선명한 넓은 화면이 줄어들며, 앞면의 흐림이 나타난 다음 닫힌 화면에서 선명해집니다. 약 10.25~11.25초의 빠른 펼침과 11.75~12.25초의 빠른 닫기는 같은 고정 재생 시간을 쓰는 것처럼 보이지 않습니다. 후반의 빠른 반복에서도 흐림이 물리적 움직임의 단계와 함께 바뀝니다.

닫기 표본 실제 약 7.47~8.22초에서는 외부 화면 왼쪽의 아이콘 열이 상대적으로 또렷한 반면 중앙과 오른쪽은 훨씬 흐립니다. 두 화면이 드러나는 구간에도 내부 오른쪽의 위젯과 아이콘은 남습니다. 약 8.47초에 흐림이 줄고 8.72초에는 대부분 선명합니다. 이 구간을 펼침 끝의 0.13~0.20초와 동일한 커브라고 단정하지 않습니다.

약 16.75~19초에는 홈 페이지를 가로로 넘기고 펼친 뒤 다시 페이지를 넘기는 장면이 있습니다. 이것은 미리 저장한 한 장의 화면만 반복해서 보여 주는 연출로는 재현할 수 없습니다. 다만 영상만으로 실시간 OS 전체 합성인지 홈 화면에 한정한 구현인지 확인할 수 없습니다.

## 첫 번째 영상과의 공통점·차이

첫 번째 영상은 흰 배경의 기기 렌더링처럼 보이며 약 11초에 걸쳐 펼침을 보여 줍니다. 앞면이 돌아가며 내부 오른쪽 영역이 먼저 보이고, 내부 왼쪽에 흐림과 가장자리 그림자가 남았다가 평평해지면서 줄어듭니다. 시계·배경의 위치가 공간적으로 이어지는 인상을 줍니다.

두 번째 영상과 공통되는 것은 움직이는 쪽의 흐림, 반대쪽의 상대적 선명도, 내용이 남아 있는 중간 상태, 끝점의 선명함입니다. 첫 번째 영상은 내부 오른쪽도 비교적 어둡고, 두 번째 영상은 밝은 홈 화면입니다. 따라서 두 영상에서 정확히 같은 블러 반경·밝기·재생 커브를 추출했다고 주장할 수 없습니다. 카메라와 기기 자체의 원근 변형을 평평한 화면 위의 추가 확대·이동 효과로 중복 적용해서도 안 됩니다.

| 움직이는 내용 | 페이지 전환·아이콘 배치가 이어짐 | 약 10fps로 얻은 한 장을 효과 중 고정하고 캡처 프레임을 버림 |
| 합성 | 화면이 한 장의 내용처럼 보임 | 불투명도 0.8의 캡처를 실제 앱 위에 겹침. 움직이는 화면에서 이중상이 생길 수 있음 |
| 방향 반전 | 다시 움직이면 그 상태로 이어지는 인상 | 표준 센서가 90→90 구간의 반전을 알리지 않아 연속 추적 불가 |

두 화면 표시 대상 오류는 0.4.0 로그에서 display=1과 실제 패널 크기로 교정된 것을 확인했습니다. 그러나 이 로그만으로 양쪽 패널에서 사용자가 매끈한 실제 내용을 봤다고 판정하지 않습니다. 패널 ON, 표시 대상 선택, 첫 프레임 제출, 육안상 연결성은 서로 다른 검증 항목입니다.

화면 전환 자체의 검은 구간과 앱 재배치도 있을 수 있습니다. 이번 로그는 센서 신호~오버레이 시작 지연을 보여 주며, 사용자 눈에 보인 모든 깜빡임의 길이를 직접 측정한 것은 아닙니다.

## 재구현에 필요한 설계

1. **내용과 효과를 분리합니다.** 원본 해상도의 선명한 내용을 유지하고, 흐림이 필요한 영역만 별도 필터링합니다. 흐림 효과 때문에 선명한 쪽을 축소해서는 안 됩니다.
2. **외부·내부에 각각 좌표계와 마스크를 둡니다.** 외부는 오른쪽으로 갈수록 강해지는 흐림, 내부는 왼쪽의 움직이는 영역을 중심으로 하는 흐림을 기준으로 맞춥니다. 관찰에 근거한 시작점이며 정확한 원본 파라미터는 아닙니다.
3. **패널 전원 전환 전에 표시 내용을 준비해야 합니다.** 패널이 켜짐 → 앱 화면 노출 → 캡처 → 강한 블러 덮기 순서로는 원본의 첫 프레임을 재현할 수 없습니다.
4. **화면 재배치도 같은 합성 과정에서 처리해야 합니다.** 외부·내부용 앱 내용을 동시에 확보하거나 시스템의 앱 표면 전환을 제어해야 합니다. 홈 화면을 직접 만드는 경우에는 콘텐츠를 고정된 쪽에 배치하고 왼쪽을 확장할 수 있습니다. 다른 앱은 해당 앱의 협조나 더 깊은 시스템 통합이 필요할 수 있습니다.
5. **효과의 진행을 입력 상태로 유지합니다.** 중간에 멈춰도 불필요하게 타이머가 끝나면 안 됩니다. 끝점 해제는 짧게 보간합니다. 90이라는 표본을 실제 90°라고 가정하지 않습니다.
6. **움직임이 되돌아오면 같은 상태에서 역으로 이어져야 합니다.** 효과를 새로 0부터 재생하는 방식은 제외합니다. 정밀 센서를 확보하지 못한 전역판은 이 동작을 완전히 만족한다고 표시하면 안 됩니다.
7. **고해상도 프레임을 CPU에서 매번 복사하는 방식은 교체 대상입니다.** GPU에서 입력 표면을 필터링하고 출력하는 방식이 적절합니다. 다만 자신의 오버레이가 다시 캡처되는 문제와 앱 표면 접근 권한을 먼저 해결해야 합니다. GPU로 바꾼다는 것만으로 시스템 전환 제약까지 사라지지는 않습니다.

## 현재 권한에서 가능한 범위

| 요구 | 현재 판정 |
|---|---|
| 양쪽 패널을 중간에 켜도록 요청 | 실기 확인. 디스플레이 상태 4/5 사용 |
| 정밀한 연속 힌지 각도 획득 | 현재 불가. 공용 센서 0/90/180, Samsung 센서는 signature\|privileged SSENSOR 필요 |
| 자기 앱 화면의 고품질 영역별 흐림·원근 렌더링 | 구현 가능. 자체 RenderNode에 RenderEffect 등을 적용할 수 있음 |
| 다른 앱의 현재 화면 캡처 | 이 실기에서 Shizuku 권한의 native capture와 GPU 버퍼 전달을 검증. MediaProjection 동의 세션으로 수명을 제한하며 보호 콘텐츠는 가림 처리 |
| 다른 앱의 앱 표면·재배치·패널 첫 프레임을 하나의 전환으로 제어 | 현재 확보한 경로로 검증되지 않음. Shizuku의 상태 요청 성공은 이 제어의 성공을 뜻하지 않음 |
| 모든 앱에서 원본과 완전히 동일한 동작 | 현재 조건에서는 제공 가능하다고 판단할 근거가 없음 |

공식 문서에서 MediaProjection은 화면을 별도의 가상 디스플레이로 캡처하는 경로이며, 크기 변경 콜백과 표면 크기 조정이 필요합니다. WindowManager는 앱 표면의 배치 정보를 관리하고 SurfaceFlinger가 화면을 합성합니다. 자기 앱 RenderNode의 블러는 이 전체 시스템 전환을 제어하는 API와 다릅니다.

- [Android MediaProjection](https://developer.android.com/media/grow/media-projection)
- [AOSP SurfaceFlinger와 WindowManager](https://source.android.com/docs/core/graphics/surfaceflinger-windowmanager)
- [Android RenderEffect](https://developer.android.com/reference/android/graphics/RenderEffect)
- [AOSP Window blurs](https://source.android.com/docs/core/display/window-blurs)

이 기기에서 window blur 지원이 false라는 결과는 **다른 창 뒤쪽을 흐리는 시스템 기능**에 대한 것입니다. 앱이 자기 픽셀을 흐리는 RenderEffect까지 사용할 수 없다는 뜻은 아닙니다.

루팅하면 무조건 된다고도 판단하지 않습니다. OEM 잠금 해제 가능 여부, 펌웨어별 앱 표면 전환 경로, 센서 접근, 보안·부팅 조건을 별도로 확인해야 합니다. 이번 작업에서 루팅이나 펌웨어 변경은 하지 않았습니다.

## 다시 시험하기 전의 수용 기준

- 선명한 앱 화면이 먼저 나온 뒤 강한 블러가 뒤늦게 덮이지 않을 것.
- 선명해야 하는 영역을 낮은 해상도의 캡처로 교체하지 않을 것.
- 외부와 내부의 종횡비가 바뀌는 순간 이전 비율의 이미지를 늘리지 않을 것.
- 중간 상태에서 멈추거나 방향을 바꾸면 효과가 임의로 새로 시작되지 않을 것.
- 두 패널 모두 화면 내용이 준비되었는지 실제 표시로 확인할 것. ON 로그만으로 통과시키지 않을 것.
- 자기 앱에서의 시각적 재현과 다른 앱에 대한 전역 적용을 각각 검증할 것.

사용자는 다른 앱을 사용하는 도중에도 적용되는 전역 기능의 개발을 계속하도록 요청했습니다. 이에 따라 실기 시험을 진행하고 있으며, 자체 앱이나 홈 화면에서만 되는 결과를 전역 기능의 완성으로 취급하지 않습니다.
