# Foldy 0.20.3 보안 점검

2026-09-14. 현재 소스, 설치된 APK, SM-F971N / Android 17, Shizuku 13.6.0.r1086.2650830c를 대상으로 확인했다. 애니메이션 개선·회전 설정 변경은 이번 점검 범위가 아니다.

설치 APK와 `artifacts/foldy-0.20.3-cover-motion.apk`의 SHA-256이 일치했다.

`51ae21349c4712917947f6d3d31524826a9e68e852a516ea5ca756ede5d85383`

현재 코드에서 화면의 외부 전송이나 이미지 파일 저장 경로는 발견하지 못했다. 그러나 화면을 지속해서 읽고 시스템 화면 위에 직접 그리는 권한을 사용하므로, 일반 설정 앱 수준의 위험으로 볼 수 없다. **디버그 설치본, 민감한 창의 오버레이 정책 미적용, 보안 상태를 구분하지 않는 프레임 캐시는 일상 사용·배포 전에 보완할 대상이다.** 실제 재현과 코드상 가능성을 아래에서 구분한다.

## 실기에서 확인한 보호

개인정보가 없는 별도 테스트 앱 `dev.foldy.securityprobe`를 일시 설치했다. 이 앱은 Shizuku·인터넷·화면 캡처·저장소 권한을 요청하지 않으며, 자체 창의 오버레이 차단을 시험하는 일반 권한만 요청한다. 녹색 테스트 화면과 빨간 합성 사각형만 사용했다. 원본 픽셀은 파일로 저장하지 않았고 메모리에서 표본 색상 개수만 집계했다. 캡처 도구는 잠금이 풀려 있고 테스트 앱이 전면에 있을 때만 동작하며 캡처 후에도 다시 확인한다.

| 시험 | 결과 | 해석 |
| --- | --- | --- |
| 별도 앱 UID에서 Foldy의 Shizuku provider 호출 | `PROVIDER_DENIED` | 일반 앱의 직접 접근 차단 확인 |
| 별도 앱 UID에서 FoldService 바인딩 | `SERVICE_DENIED` | 비공개 서비스 접근 차단 확인 |
| 일반 테스트 창, 현재 NativeFrameCapture 사용 | 녹색 900/900 | 검사 위치와 캡처 경로의 양성 대조군 확인 |
| 같은 창에 FLAG_SECURE 설정 | 검정 900/900, 녹색 0 | 이 펌웨어에서 보안 창 원본을 제외하는 경로 확인 |
| 오버레이 차단 창, 합성 레이어 없음 | 녹색 900/900 | 정상 테스트 내용 표시 |
| 오버레이 차단 창, Foldy와 같은 root SurfaceControl 방식의 빨간 레이어 | 빨강 900/900 | 창의 오버레이 차단이 해당 레이어를 숨기지 못함 |
| FLAG_SECURE와 오버레이 차단을 함께 설정하고 같은 레이어 표시 | 빨강 900/900 | 보안 창 원본은 보호되지만 별도로 합성한 레이어까지 보호·차단되는 것은 아님 |

마지막 두 시험은 Foldy와 같은 shell UID·root SurfaceControl·레이어 높이를 이용한 합성 도구로 재현했다. 제품 애니메이션의 모든 프레임이나 실제 금융 앱에서 재현한 결과로 확대 해석하지 않는다. 빨간 픽셀은 도구가 만든 사각형이며, 보안 창의 원본을 우회해 읽은 결과가 아니다.

프레임워크를 직접 조회한 결과, 현재 코드에 지정된 보안·보호 콘텐츠 정책 `0`은 각각 `SECURE_CONTENT_POLICY_REDACT`, `PROTECTED_CONTENT_POLICY_REDACT`였다. 보호 콘텐츠 정책의 상수 의미는 확인했지만 DRM 동영상은 별도로 재생·시험하지 않았다. Android의 [민감한 창 보호 문서](https://developer.android.com/security/fraud-prevention/activities)는 FLAG_SECURE와 오버레이 차단을 서로 다른 보호로 설명한다.

검사 소스: `tools/security_probe/`. 결과: Git 제외 경로 `measurements/security-0.20.3/`의 `synthetic-capture.txt`, `component-boundaries.txt`, `capture-policy.txt`, `installed-manifest.txt`. 초기 도구는 컴포넌트 이름 형식을 잘못 비교해 캡처를 모두 건너뛰었다. 이를 수정한 뒤의 위 성공 결과만 판단 근거로 사용했다. 테스트 앱과 휴대전화의 임시 도구는 제거하고 Foldy 화면으로 돌아왔다.

## 확인된 위험과 보완 순서

### 1. 디버깅 가능한 설치본 — 실기 확인, 배포 전 필수 보완

설치된 패키지에 `DEBUGGABLE`이 설정돼 있고 APK에도 `android:debuggable=true`가 들어 있다. 승인된 ADB에서 `run-as dev.poldy.lab id`가 성공해 Foldy 앱 UID로 실행 가능한 것을 확인했다. 앱 파일 내용이나 메모리를 추출하는 시험은 하지 않았다. Shizuku 사용자 서비스의 `.debuggable(false)`는 앱 APK의 디버그 속성을 끄는 설정이 아니다.

공격에는 승인된 ADB 접근 등 추가 조건이 필요하며, 인터넷의 임의 사용자가 곧바로 접근할 수 있다는 의미는 아니다. 그러나 화면 버퍼와 권한 연결을 가진 앱이므로 디버그 가능 상태는 노출을 키운다. Android도 [배포 앱에서 debuggable을 끌 것](https://developer.android.com/privacy-and-security/risks/android-debuggable)을 안내한다.

전용 서명 키를 사용한 비디버그 릴리즈 빌드로 바꾸고 설치본의 최종 manifest를 검사해야 한다. 현재는 Android Debug 인증서로 서명돼 있다. 이것이 모든 Android 개발자와 같은 개인 키를 쓴다는 뜻은 아니며, 다른 서명의 APK가 기존 앱을 자유롭게 덮어쓸 수 있다는 뜻도 아니다.

### 2. 민감한 창의 오버레이 차단과 호환되지 않는 합성 레이어 — 실기 재현

`NativeScene`은 일반 애플리케이션 오버레이 창이 아닌 root SurfaceControl을 직접 만든다. 같은 방식의 시험 레이어는 `setHideOverlayWindows(true)`인 창 위에도 남았다. 따라서 앱이 오버레이 차단을 요청한다고 해서 Foldy 효과가 자동으로 사라진다고 보장할 수 없다.

현재 코드에 결제 버튼 클릭이나 키 입력을 주입하는 기능은 없다. 다만 전환 중 보관한 화면이 실제 앱·권한 창 위를 덮을 수 있어, 보이는 내용과 실제 입력 대상이 잠시 달라질 위험을 검토해야 한다. 금융·인증·권한 확인 화면에서는 효과를 자동 중지하고, 판별이 불확실할 때도 보관 화면을 표시하지 않는 정책이 우선이다. 사용자 지정 제외 앱도 필요하다.

### 3. 보관 프레임에 보안 상태가 연결돼 있지 않음 — 코드상 경로 확인, 시각적 유출 미재현

`PanelFrameCache`는 사용자·작업·Activity로 소유자를 구분하고 반대 패널의 원본 화면을 최대 15초 동안 재사용한다. `TaskProfileReader`는 창의 FLAG_SECURE 여부를 읽지 않으며, 캡처 결과에도 보안 콘텐츠 포함 여부를 전달하지 않는다. 같은 Activity가 일반 화면에서 보안 화면으로 바뀌면 소유자 문자열은 같을 수 있다. 한 패널의 새 캡처가 검게 처리돼도 반대 패널의 이전 일반 화면은 별도 무효화되지 않을 수 있다.

또한 `NativeScene`의 출력 레이어는 secure surface로 지정돼 있지 않다. 이는 새 보안 화면의 원본을 캡처할 수 있다는 의미가 아니라, **보호 전 만들어 둔 화면 이미지에 이후의 보호 상태가 자동으로 전달되지 않는 문제**다. 잠금 시에는 수집 중지와 자원 해제 코드가 있으나, `pauseForLock()`은 제어 프로세스의 복구를 기다린 뒤 패널 버퍼를 해제한다. 그 대기 중 잔상이 노출되는지까지 실기로 검사하지는 않았다.

보안 상태 변화 때 양쪽 캐시·전환용 프레임을 함께 폐기하고, 잠금·민감한 창 감지 시 먼저 합성 레이어를 숨긴 뒤 복구 작업을 해야 한다. 필요하면 합성 레이어 자체의 secure 속성도 적용한다. 이후 같은 Activity의 보안 전환, 생체 인증, 잠금과 접힘이 겹치는 상황을 합성 테스트로 재검증해야 한다.

### 4. 접지 않을 때도 화면을 읽는 구조 — 코드 확인

서비스가 켜져 있고 잠금이 풀려 있으면 화면 캡처가 계속된다. `FoldService.captureNext()`는 움직임·전환 중 약 16ms, 대기 중 약 80ms 간격을 목표로 한다. 따라서 보호되지 않은 메시지·업무 문서·화면상 개인정보도 전면에 있으면 GPU 버퍼에 들어올 수 있다. 키보드 입력이나 파일 내용을 별도로 수집하는 코드가 있다는 뜻은 아니다.

전면 앱이 실제로 달라지면 캐시를 지우며, 잠금·종료 때는 해제하는 코드가 있다. 이미지 파일 저장, HTTP·소켓 전송, 분석·광고 SDK는 점검한 소스와 앱 의존성에서 찾지 못했다. `allowBackup=false`와 데이터 추출 제외 규칙도 설정돼 있다. 개발 과정에서 Mac에 수집한 스크린샷·로그는 앱의 자동 저장과 별개이며, 기존 측정 자료 전체의 개인정보 검사는 이번 범위에 포함하지 않았다.

온보딩에 지속 화면 처리 사실을 명시하고, 민감한 앱 제외·캐시 보관 최소화·필요한 시점만 수집하는 방식을 검토해야 한다. 보간에 필요한 준비 시간과 개인정보 처리 범위를 함께 평가할 사항이다.

### 5. Shizuku 권한 범위와 인터넷 권한 해석 — 실기·코드 확인

Foldy의 일반 앱 프로세스와 별도로 `display_control` 및 Shizuku 서버는 shell UID 2000으로 실행 중이었다. 현재 부트로더 잠금 값은 1, Verified Boot 상태는 green이었다. 이 기능을 위해 루트 UID 프로세스로 실행하고 있지는 않다.

Foldy APK에 INTERNET 권한은 없지만 shell 패키지는 INTERNET 권한을 갖고 있다. 따라서 **앱에 INTERNET 권한이 없다는 사실만으로 권한 있는 제어 프로세스의 통신까지 기술적으로 불가능하다고 말할 수 없다.** 현재 전송 경로를 발견하지 못했다는 판단과, 향후 변조된 코드·악성 업데이트의 능력은 구분해야 한다. Shizuku 권한은 애니메이션 기능에만 한정된 OS 권한이 아니다. [공식 API 설명](https://github.com/RikkaApps/Shizuku-API/blob/master/README.md)은 UserService가 shell/root 신원으로 코드를 실행한다고 설명한다.

Manifest의 provider는 `INTERACT_ACROSS_USERS_FULL` 권한으로 보호되며 일반 앱 접근 차단을 재현했다. [Shizuku 공식 서버 코드](https://raw.githubusercontent.com/RikkaApps/Shizuku-API/master/server-shared/src/main/java/rikka/shizuku/server/Service.java)도 사용자 서비스 연결 전 권한을 검사한다. 다만 Foldy `DisplayControl` 각 Binder 메서드에는 별도의 호출 UID 검사·allowlist가 없다. 현재 바인더 배포 경로의 보호에 의존하며, 일반 앱의 직접 악용은 이번 검사에서 발견하지 못했다. 방어를 강화하려면 각 호출에서 Foldy의 UID와 필요한 관리 호출만 허용해야 한다. 공식 서버 소스 참고는 설치된 Shizuku 바이너리 전체를 감사한 것과 같지 않다.

### 6. USB 디버깅 신뢰 관계 — 실기 확인

| 항목 | 현재 값 |
| --- | --- |
| 개발자 옵션 | 켜짐 |
| USB 디버깅 | 켜짐 |
| 무선 디버깅 | 꺼짐 |
| 레거시 ADB TCP 포트 속성 | 설정값 없음 |
| ADB 인증 요구 `ro.adb.secure` | 1 |
| ADB 승인 연결 만료 `adb_allowed_connection_time` | 0 |

연결 만료 0은 이전에 승인한 키를 자동 만료시키지 않는 값이다. [AOSP의 승인 키 처리](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/core/java/com/android/server/adb/AdbDebuggingManager.java)에서 확인했다. 신뢰한 Mac이나 그 ADB 개인 키가 탈취되면 이 신뢰 관계가 문제가 될 수 있다. USB를 꽂는 모든 컴퓨터를 자동 승인한다는 뜻은 아니다. [Android ADB 문서](https://developer.android.com/tools/adb)는 신규 컴퓨터의 키 승인과 무선 페어링을 설명한다.

이 값을 언제 누가 설정했는지는 이번 검사로 판단하지 않았다. 현재 Foldy에는 이 설정을 쓰는 코드가 없고, 이번 점검에서도 수정하지 않았다. 모르는 컴퓨터를 승인하지 않고, 오래된 승인·불필요한 무선 디버깅을 정리하는 방식으로 관리할 수 있다. 디버깅을 끄면 Shizuku 사용 방식에 영향을 줄 수 있으므로 앱 설정에서 몰래 바꾸면 안 된다.

## 범위와 후속 조치

이번 점검은 소스·설치 APK·제한된 실기 재현을 결합한 앱 보안 검토다. 전체 펌웨어, 모든 Shizuku 코드와 서드파티 바이너리, GPU 드라이버, 모든 금융 앱, 잠금 경합, 네트워크 트래픽 전수 관찰까지 완료한 인증이나 침투 테스트는 아니다. 다른 앱의 개인 파일·메시지·금융 데이터는 읽지 않았다.

후속 구현 순서는 **민감한 창 자동 중단과 캐시 폐기 → 잠금 시 레이어 즉시 숨김 → 비디버그 릴리즈 및 전용 서명 → 호출 UID 검증과 지속 캡처 범위 축소**가 적절하다. 사용자가 회전 부분은 괜찮다고 했으므로 이 보안 작업에 회전 설정 재설계는 포함하지 않는다.

현재 Foldy 제품 소스·설치 버전·개발자 옵션을 바꾸지는 않았다. 변경 사항은 이 점검 문서와 개인정보 없는 보안 검사 도구다.
