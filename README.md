# Poldy — 화면 전환부터 검증하는 새 구현

현재 시험판: **0.14.0-native-home**. 내부 화면에서 외부용 홈 배치가 넓게 표시되던 문제를 수정했습니다. 화면 크기만 강제로 바꾸던 경로를 제거하고 실제 내부·외부 화면 구성을 전환합니다. 이때 두 패널의 원본 크기 화면을 임시 출력으로 유지한 뒤 시스템 출력으로 함께 돌려보냅니다. 화면 전환 완료 후에는 실제 앱이 기본 입력 경로로 동작합니다. [원인과 실기 비교](research/home-layout-0.13.md).

0.13.1의 블러 반경, 부드러운 경계, 절제된 평면 변형과 HAL 각도 입력·보간은 유지했습니다. [시각 효과 검증](research/soft-diffusion-0.13.md), [중간 각도 입력 경로](research/hal-angle-log-path.md). 홈 구성을 정상화하려고 물리 매핑 경로를 바꿨으므로 과거 버전의 무깜빡임 사용자 확인을 이번 버전의 결과로 간주하지 않습니다. 이번 버전의 전환 깜빡임·회전·중간 반전은 별도 실기 확인 대상입니다.


2026-09-11. macOS에서 개발합니다. 다른 작업의 애니메이션 코드·설계는 사용하지 않습니다.

목표는 사용자가 전달한 세 동영상의 접힘 각도에 따른 흐림·공간감·화면 연결감을, 홈 화면과 다른 앱 사용 중 모두 구현하는 것입니다. 현재 산출물은 **실기 검증 중인 애니메이션 시험판과 진단 도구**입니다. USB 상태 요청으로 조기 점등을 양방향 확인했고, 앱에서는 Shizuku로 해당 제어를 연결합니다. 원본 영상처럼 연속적인 물리 각도를 추적하는 완성품은 아닙니다.

**아래는 0.8.4~0.13.1의 이전 전환 방식과 당시 검증 결과입니다. 현재 소스는 위의 0.14.0입니다.** 0.7.1에서는 양방향 검은 깜빡임을 재현했습니다. 0.8부터 물리 출력 매핑을 외부 주 화면 상태 5에 유지하고, 앱의 논리 크기만 비저장 방식으로 바꿉니다. 내부에는 시스템의 실시간 화면 복제를 표시합니다. **사용자는 0.8.3에서 순간 검정이 보이지 않는 것 같고, 내부 화면의 스크롤·버튼과 펼침 시작의 외부 흐림이 정상이라고 확인했습니다.** 모든 조건의 무깜빡임이나 원본의 프레임 단위 동일 재현을 보장하는 것은 아닙니다.

0.8.1의 정지 상태 자동 왕복 전환 녹화는 내부 198프레임·외부 169프레임에서 전체 검정 프레임이 없었습니다. 0.8.0의 실제 접힘 중 별도 정지 캡처에는 완전 검정 이미지도 있어, 녹화만으로 물리 OLED의 깜빡임 제거를 단정하지 않습니다. 내부 터치는 시스템의 `CLONE` 입력 창으로 앱에 직접 전달되며, 별도 이벤트 재주입 코드를 제거했습니다. 0.8.4는 전환 종료 뒤 반대 화면에도 현재 앱을 갱신해 이전 앱이 남지 않도록 하고, 흐림 진입을 180ms 동안 진행합니다. 제어 프로세스 강제 종료 실험에서 별도 복구 감시자가 약 0.74초 안에 화면 상태와 크기를 기본값으로 복구했습니다. 빌드·14개 Java 테스트·Lint(오류 0, 경고 24)를 통과했습니다.

자세한 실험과 남은 문제는 [검은 깜빡임 조사](research/black-flash-investigation.md)에 기록했습니다.

0.4.0은 사용자 기준을 만족하지 못했습니다. 12회 전환에서 효과가 567~730ms 늦게 시작했고 내부 화면의 약 10.7% 픽셀 수로 만든 캡처가 확대됐습니다. [원본 141개 표본과 실행 로그 분석](research/reference-animation-analysis.md)을 바탕으로 캡처와 렌더링 경로를 다시 구현했습니다. 원본과 완전히 동일한 전역 애니메이션을 달성했다고 주장하지 않습니다.

## 지금 확인할 문제

0.11.2 사용자 재시험에서도 중간 효과 정체와 끝점 몰아 진행이 남았습니다. 끝점 신호에서 추정값이 펼침 약 54°·접힘 약 157°로 크게 어긋난 기록을 확인했습니다. 일반 공개 센서는 0/90/180이며 전용 센서 직접 구독은 시스템 권한으로 거부됩니다. **후속으로 현재 펌웨어의 HAL 로그에서 중간 각도 값을 읽는 경로를 발견했습니다. 90초 실시간 측정에서 194개 표본·115개 각도·1–179°를 확인했고, 0.12.0에서 애니메이션에 연결했습니다. 앱에서도 265개 표본을 확인했습니다. 0.12.1은 늦은 공개 자세 대신 측정 각도로 효과를 시작하고 끝점 확인을 기다립니다. 사용자는 0.12.1에서 이전과 달리 각도를 잘 따라온다고 확인했으나 중간 끊김을 보고했습니다. 0.12.2에서 희소한 각도 표본 사이의 보간을 조정한 뒤 사용자가 끊김이 많이 줄었다고 확인했습니다. 0.13.0은 이 입력·보간을 유지한 채 시각 효과만 다듬었으며 체감 검증은 진행 중입니다.** [HAL 로그 경로](research/hal-angle-log-path.md), [공식 API·권한 조사와 수정된 판단](research/hinge-angle-access-2026-09-11.md). 시각 효과의 테스트 통과를 실제 각도 추적 성공으로 해석하지 않습니다.

사용자 관찰: 접힌 기기를 펼칠 때 내부 화면이 약 90°에서 켜지고, 펼친 기기를 접을 때 외부 화면이 약 5°에서 켜집니다. 실제 기기의 상태 전환을 측정했지만 표준 센서가 세 값만 전달하므로 삼성의 정확한 임계각으로 단정하지 않습니다.

화면이 꺼져 있는 구간에는 애니메이션을 그려도 보이지 않습니다. 실제 기기에서 내부·외부 화면 모두 30~45°에서 조기 표시할 수 있음을 사용자 육안 확인과 시스템 덤프로 검증했습니다. 이후 자동 전환과 효과를 구현했고, 사용자가 요청한 두 화면 동시 표시를 추가했습니다.

## 구성

- `app/`: Poldy Lab. 두 물리 패널의 동시 표시, 원본 해상도의 GPU 캡처, 비대칭 Gaussian 흐림, 전환 준비와 끝점 드러내기를 구현합니다. 시험 실행과 진단 측정은 각각 최대 5분입니다.
- `tools/device_probe.py`: macOS용 읽기 전용 ADB 수집 도구. 상태 덤프·지원 명령·센서 로그를 저장합니다. 기기 설정이나 화면 상태를 바꾸지 않습니다.
- `tools/test_device_probe.py`: 같은 논리 화면 ID의 패널 전환, 펼침/접힘 구분, 누락된 각도, 화면 삭제/추가를 확인합니다.
- `research/feasibility.md`: 공식 문서 확인 내용과 기기 연결 후 판정 기준.

센서 진단 기능은 화면 내용을 캡처하지 않습니다. 별도 ‘고해상도 경로 진단’은 효과 레이어를 캡처에서 제외할 수 있는지 기기 메모리에서 확인합니다. 애니메이션 기능은 Android 화면 공유 동의를 받아 프레임을 메모리에서만 처리하며 이미지 저장·전송을 하지 않습니다. 앱에 네트워크 권한은 없습니다. 진단 파일은 앱 내부 저장소에 JSONL로 저장하고 디버그 APK의 `run-as`로 읽습니다. 화면 wakelock은 사용하지 않습니다.

## 빌드

Android Studio의 JDK와 설치된 Android SDK 36을 사용합니다. 다른 Mac에서는 `local.properties`의 `sdk.dir`을 해당 SDK 경로로 맞춥니다.

```sh
export JAVA_HOME='/Applications/Android Studio.app/Contents/jbr/Contents/Home'
./gradlew :app:assembleDebug :app:testDebugUnitTest :app:lintDebug
python3 -m unittest discover -s tools -p 'test_*.py'
```

APK: `app/build/outputs/apk/debug/app-debug.apk`

## 휴대전화 연결 후

1. 데이터 전송이 가능한 USB 케이블로 Mac에 연결합니다.
2. 휴대전화의 개발자 옵션에서 USB 디버깅을 켜고 이 Mac의 디버깅 요청을 승인합니다.
3. 아래 명령은 프로젝트 폴더에서 실행합니다. 실제 휴대전화가 여러 대면 Python 명령에 `--serial SERIAL`을 추가합니다. 설치 명령의 `-d`는 실제 기기가 한 대일 때 사용합니다.

```sh
python3 tools/device_probe.py inventory --directory measurements/baseline
~/Library/Android/sdk/platform-tools/adb -d install -r app/build/outputs/apk/debug/app-debug.apk
~/Library/Android/sdk/platform-tools/adb -d shell am start -n dev.poldy.lab/.MainActivity
```

Poldy Lab에서 ‘측정 시작’을 누릅니다. 다른 앱으로 이동해 천천히 2~3회 접었다 펼치면서 Mac에서 아래 명령을 실행합니다. 어느 각도에서 실제 화면이 보이는지도 함께 관찰합니다.

```sh
python3 tools/device_probe.py watch --seconds 30 --directory measurements/baseline
```

앱이나 알림에서 측정을 종료한 뒤 저장된 원본을 가져옵니다.

```sh
python3 tools/device_probe.py pull --directory measurements/baseline
python3 tools/device_probe.py summarize --directory measurements/baseline
```

`transitions.json`은 앱에 보이는 **논리 디스플레이 변화**입니다. 실제 패널 점등과 같은 뜻이 아닙니다. `system-timeline.jsonl`의 물리 디스플레이 상태 및 관찰 결과와 대조합니다. 앱 센서 기록의 `elapsed_ms`는 휴대전화 시간축, 시스템 덤프의 `host_*_epoch_ms`는 Mac 시간축입니다. 두 시계가 정확히 동기화됐다고 가정하지 않습니다. `angle_age_ms`는 마지막 센서 표본의 나이이며 값이 크면 전환 순간의 각도로 확정하지 않습니다.

## 애니메이션 시험판 사용

Shizuku v13.6.0을 공식 배포본에서 설치했으며 이 Mac의 ADB로 서버를 시작했습니다. 다음 순서로 사용합니다.

1. Poldy Lab에서 ‘화면 제어 연결’을 누릅니다. 처음 한 번 Shizuku 접근을 허용합니다.
2. ‘다른 앱 위에 표시 허용’에서 Poldy Lab을 허용합니다.
3. ‘애니메이션 시작’을 누르고 Android의 전체 화면 공유에 동의합니다.
4. 완전히 접힌 상태에서 시험을 시작한 후, 다른 앱에서 접었다 펼칩니다. 현재 화면 전환 시험은 기본 세로 방향을 대상으로 합니다.
5. 앱 또는 알림의 중지 버튼으로 종료합니다. 화면 공유 종료·화면 잠금·5분 경과 시에도 중지합니다.

Shizuku는 일반적으로 재부팅 후 다시 시작해야 합니다. 무선 디버깅을 사용하면 휴대전화에서도 시작할 수 있습니다. [공식 안내](https://shizuku.rikka.app/guide/setup/).

## 구현 범위

- Android 기본 window blur가 지원되지 않아 원본 해상도 GPU 버퍼에 RenderEffect Gaussian blur를 그립니다. 효과는 내부 왼쪽과 외부 오른쪽에 집중하며, 완전히 접거나 펼치면 현재 표시 각도에서 끝점으로 점진 보정합니다. 새 화면 준비와 시각 효과 정리가 모두 끝난 뒤 실제 앱을 드러냅니다.
- Android 전체 화면 공유 세션과 Shizuku 연결이 모두 있어야 시작합니다. 실제 프레임은 Android 17의 ScreenCaptureInternal을 통해 GPU 버퍼로 전달합니다. 일반 앱의 공개 캡처 API만으로 구현한 기능은 아니며 펌웨어 변경에 영향을 받을 수 있습니다.
- 애니메이션 레이어를 캡처에서 제외해 효과가 다음 캡처에 섞이지 않도록 합니다. 보호·보안 콘텐츠의 캡처 정책은 REDACT(0)로 고정합니다.
- 두 패널의 전원 임대를 1초마다 갱신하고 물리 주 패널은 외부로 유지합니다. 앱 논리 크기는 1248×1972와 2448×1848 사이에서 바꾸되 사용자 설정으로 저장하지 않습니다. 내부에는 실제 앱의 시스템 미러를 표시하고, 반대 패널의 전환 중 미리보기에는 직전 프레임을 유지하고, 전환 후에는 현재 앱 화면을 비율에 맞춰 갱신합니다. 두 개의 독립적인 앱 배치를 동시에 실행하는 기능은 아닙니다.

- 두 패널의 비율이 다르면 화면을 자르거나 찌그러뜨리지 않고 전체가 들어가도록 가운데 맞춥니다. 이 경우 여백이 생깁니다. 대상 앱의 새 배치를 확보하기 전 대기 화면까지 원본 동영상과 같다고 보장하지 않습니다.
